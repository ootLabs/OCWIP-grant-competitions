# Mapa: infrastruktura

Docker, bootstrap bazy, skrypty jakości, CI, zmienne środowiskowe.

| Plik | Co robi |
|---|---|
| `docker-compose.yml` | Trzy usługi: `db` (postgres:16-alpine, healthcheck, wolumen `postgres-data`), `backend` (.NET, `dotnet watch`, port 8080), `frontend` (Next.js dev, port 3000, `API_SERVER_URL` na nazwę usługi `backend`, bo strony publiczne z T-23 renderują się na serwerze wewnątrz kontenera). Wolumeny nazwane `backend-obj` i `backend-bin` chronią build kontenera przed hostowym `bin/obj`, a `attachments-data` (T-32) trzyma przesłane załączniki wniosków poza bind mountem. Konfiguracja backendu jedzie zmiennymi z podwójnym podkreśleniem (`ConnectionStrings__Postgres`, `Cors__Origins`, `Auth__SessionLifetimeHours`, `Auth__CookieSameSite`, `Auth__SecureCookie`, `Auth__MaxFailedLoginAttempts`, `Auth__LockoutMinutes`, `RateLimiting__PermitLimit`, `RateLimiting__WindowSeconds`, `Attachments__StoragePath`); `Auth__SecureCookie` jest **puste**, nie `false`, żeby lokalny wyjątek na http nie pojechał na produkcję, a cztery przed ostatnią to progi ochrony przed brute force z T-12.5 T-113: `DataProtection__KeysPath` i wolumen `dataprotection-keys` na `/data/keys` backendu.; `mailpit` (T-100) tylko w profilu `test`, skrzynka testu w przeglądarce |
| `docker-compose.prod.yml` | Produkcja na jednej maszynie (T-111): `db` (obraz z rolami), `migrate` (jednorazowo, przed API), `backend` w `Production`, `frontend` z `NEXT_PUBLIC_API_URL` jako argumentem budowania, `caddy` jako jedyny z portami (80, 443, zmienne `HTTP_PORT`/`HTTPS_PORT` dla maszyn bez niskich portów); bez bind mountów, sekrety wymagane przez `${VAR:?}`, healthchecki, `restart: unless-stopped`, limity logów, sieć `172.30.0.0/24` zaufana dla nagłówków przekazanych |
| `.env.example` | Nazwy wszystkich zmiennych środowiskowych z bezpiecznymi placeholderami: Postgres, porty, `DATABASE_URL`, `CORS_ORIGINS`, adres frontu do linków w mailach i lista hostów (`FRONTEND_BASE_URL`, `ALLOWED_HOSTS`, T-91, sprawdzane przy starcie w `Production`), ciasteczko sesji (`AUTH_SESSION_LIFETIME_HOURS`, `AUTH_COOKIE_SAME_SITE`, `AUTH_SECURE_COOKIE`), ochrona przed brute force (`AUTH_MAX_FAILED_LOGIN_ATTEMPTS`, `AUTH_LOCKOUT_MINUTES`, `RATE_LIMIT_PERMIT_LIMIT`, `RATE_LIMIT_WINDOW_SECONDS`), przechowywanie załączników (`ATTACHMENTS_STORAGE_PATH`, T-32), zadania w tle (`BACKGROUND_JOBS_ENABLED`, `BACKGROUND_JOBS_INTERVAL_SECONDS`, T-105), przekaźnik poczty (`SMTP_HOST`, `SMTP_PORT`, `SMTP_ENABLE_SSL`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_FROM`, `SMTP_FROM_NAME`, T-43a) oraz adresy dla frontu (`NEXT_PUBLIC_API_URL` dla przeglądarki, `API_SERVER_URL` dla renderowania po stronie serwera, `OPENAPI_URL` dla generatora klienta). Nigdy nie trafia tu prawdziwy sekret T-113: `DATA_PROTECTION_KEYS_PATH`.; `MAILPIT_PORT` (T-100); notka o limiterze za proxy poprawiona w T-111: `ForwardedHeaders__KnownNetworks`, nie `ASPNETCORE_FORWARDEDHEADERS_ENABLED` |
| `.env.prod.example` | Ustawienia `docker-compose.prod.yml` (T-111): domena, TLS Caddy, trzy hasła bazy, klucz szyfrowania, przekaźnik poczty, limit logowania; kopia jako `.env.prod`, poza gitem |
| `deploy/caddy/Caddyfile` | Wejście publiczne (T-111): TLS (`CADDY_TLS`: e-mail dla Let's Encrypt albo `internal`), HSTS, kompresja, limit ciała 26 MiB jak Kestrel, `/api/*` na backend ze zdjętym prefiksem, reszta na front; admin API tylko w kontenerze |
| `deploy/caddy/Dockerfile` | Obraz Caddy z Caddyfile w środku, bo compose produkcyjne nie montuje ścieżek z hosta |
| `deploy/db/Dockerfile` | Obraz PostgreSQL z `db/init` i skryptem ról w `docker-entrypoint-initdb.d` (T-111) |
| `deploy/db/010-roles.sh` | Pierwszy start pustego wolumenu: role `ocwip_migrator` i `ocwip_app` z hasłami ze zmiennych przez zmienne psql, prawo `CREATE` tylko dla migratora (T-113, T-111) |
| `.editorconfig` | Kodowanie, końce linii, wcięcia. 4 spacje w C#, 2 w reszcie |
| `backend/Dockerfile` | Obraz deweloperski na `mcr.microsoft.com/dotnet/sdk:10.0`. Restore w osobnej warstwie. Globalnie zainstalowany `dotnet-ef` 10.0.4 (migracje bez SDK na hoście) |
| `frontend/Dockerfile` | Obraz deweloperski na `node:22-alpine`. `npm install` w osobnej warstwie z tego samego powodu |
| `backend/Dockerfile.prod` | Obraz produkcyjny API (T-110): etap `sdk` robi `dotnet publish -c Release` samego projektu API (bez testów), runtime to `aspnet:10.0` jako użytkownik `app` (UID 1654) z `libgssapi-krb5-2` dla Npgsql, pliki `backend/seed/` w `/app/seed` dla importu treści (T-96) i `/data/attachments` należące do `app`. Build pada, gdy w obrazie nie ma `Europe/Warsaw` T-113: cel `migrate` (bundel migracji EF, `./efbundle`, połączenie z `ConnectionStrings__Postgres`) oraz `/data/keys` należące do `app` i `DataProtection__KeysPath=/data/keys`. |
| `frontend/Dockerfile.prod` | Obraz produkcyjny frontu (T-110): `npm ci`, `next build` z `NEXT_PUBLIC_API_URL` jako argumentem builda (znika przy jednym originie, T-111), runtime to sam wynik `standalone` z `.next/static` i `public/`, `node server.js` jako użytkownik `node`; `API_SERVER_URL` domyślnie `http://backend:8080` |
| `db/init/001_extensions.sql` | Od T-113 pusty poza komentarzem: rozszerzenia nie są potrzebne (`gen_random_uuid()` jest wbudowane), strefę UTC ustawia połączenie aplikacji, a zarządzany PostgreSQL i tak nie uruchamia `db/init`. Zostaje jako miejsce na to, czego migracja nie umie |
| `scripts/check_map.py` | Wykrywa rozjazd między repozytorium a `docs/map/`: pliki niezmapowane, wiersze wskazujące na nieistniejące pliki, wiersze w złym obszarze, nieznane katalogi najwyższego poziomu. `AREAS` i `KNOWN_TOP_LEVEL` to miejsca do rozszerzania; od T-100 obszar `e2e` (`docs/map/e2e.md`); od T-111 `docker-compose.prod.yml`, `.env.prod.example` i `deploy/` w obszarze infra |
| `scripts/check_text.py` | Blokuje myślniki typograficzne (em dash, en dash, kreska pozioma) w całym repozytorium. Znaki trzyma jako `\u` escape, żeby nie wywracać się na własnym źródle |
| `scripts/smoke_test.py` | Rozmawia z działającym stackiem po HTTP: `/health`, `/health/db`, strona startowa frontu. Łapie awarię, której testy jednostkowe nie złapią; od T-111 `SMOKE_BACKEND_URL`, `SMOKE_FRONTEND_URL`, `SMOKE_INSECURE`, `SMOKE_RESOLVE` i `SMOKE_EXPECT_NO_OPENAPI` do przebiegu przez Caddy compose produkcyjnego |
| `scripts/seed.py` | Wstawia dane testowe do **pustej** bazy przez `docker compose exec db psql` (od T-38b także obie karty oceny 2026 z `backend/seed/evaluation-cards` i wszystkie trzy wskazania wersji w konkursie): operator, dwóch wnioskodawców, konkurs, wersja formularza, wniosek złożony i roboczy, załącznik. Odmawia, gdy w bazie są wiersze, a także gdy baza ma tabelę, której skrypt nie zna, bo wtedy sprawdzenie pustości nie pokrywa całego schematu. Stałe identyfikatory i hasła jako jawny placeholder, więc żadne konto się nie zaloguje. Zestaw wierszy opisuje [`model-danych.md`](../model-danych.md) T-94: formularz wniosku z `backend/seed/forms/application-2026.json`, złożony wniosek z kompletem odpowiedzi 2026 i `applicant_type`.; od T-95 także wzór sprawozdania 2026 (`report-2026.json`), podpięty pod konkurs; lista `TABLES` uzupełniona o tabele z T-47a, T-102, T-103, T-105 i T-107 |
| `scripts/runbook.py` | Napędza kolejkę zadań z [`../runbook/kolejka.md`](../runbook/kolejka.md) i bramkę ukończenia. `doctor` (stan gałęzi, drzewa roboczego, hooków, `.env`, kontenerów i spójności kolejki, `--fix` naprawia bezdecyzyjne), `next` (pierwsze zadanie o zamkniętych zależnościach), `status` (cała kolejka), `gate` (sześć kroków bramki, `--fast` bez smoke testu). Tabela kolejki jest parsowana po pozycji kolumn, więc `COLUMNS` to kontrakt. Kroki bramki wołają `sys.executable`, a nie `python`: gołego `python` nie ma na większości instalacji Linuksa i bramka padała na pierwszym kroku z `python not found`, obwiniając o to mapę repozytorium |
| `.githooks/pre-commit` | Uruchamia oba checki przed commitem. Włączany raz na klon: `git config core.hooksPath .githooks` |
| `.github/workflows/ci.yml` | Pięć zadań na każdym pull requeście: checks, backend (skan pakietów NuGet, testy przeciwko prawdziwemu PostgreSQL), frontend (audyt zależności produkcyjnych, typecheck, testy, build), smoke test na trzech kontenerach. Zadanie backendu nadpisuje `Attachments__StoragePath` na katalog w `runner.temp` (T-32): domyślna z `appsettings.json` (`/data/attachments`) zakłada wolumen Dockera, którego to zadanie nie ma, uruchamiając `dotnet test` wprost na maszynie Piąte (T-110) buduje oba obrazy produkcyjne, sprawdza, że żaden nie działa jako root, i puszcza smoke test na samych obrazach we wspólnej sieci, w środowisku Staging; od T-113 z dwiema rolami bazy: migracja obrazem `migrate` rolą `ocwip_migrator`, sprawdzenie, że `ocwip_app` nie ma praw DDL, API na `ocwip_app`; od T-100 szóste zadanie `e2e`: stos z Mailpitem, Playwright, nagranie przy porażce; od T-111 zadanie `production`: compose produkcyjne z Caddy i certyfikatem wewnętrznym na `ocwip.test`, smoke test przez proxy bez `/openapi`, tylko porty 80 i 443, HSTS |
